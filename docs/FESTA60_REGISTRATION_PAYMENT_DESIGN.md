# 60周年FESTA 申込・決済・メール設計

更新日: 2026-08-08

## 1. 目的と適用範囲

本書は、60周年FESTAの正式申込、参加費・寄付の決済、入金確認、メール通知、当日受付までの設計をまとめたものです。公開フォーム、Cloudflare Pages Functions、D1、外部決済代行サービス、メール送信サービス、管理画面を対象とします。

新規申込の締切は2027年1月31日23:59（日本時間）です。公開フォームとAPIの双方で締切を判定し、締切後は新規申込、銀行振込先の新規確認、支払方法の新規切替を受け付けません。締切前に成立した申込の決済完了、入金照合、メール送信、事務局による変更対応は継続します。

個人情報はD1と承認済みの外部サービスだけで取り扱い、GitHub、公開JSON、静的HTMLには保存しません。カード番号、ウォレット認証情報、振込元口座情報はFANTASISTAでは取得・保存しません。

## 2. 重大な問題1〜5と対処

| No. | 重大な問題 | 対処 |
|---|---|---|
| 1 | 振込先を表示しただけの段階で送金されると、申込とPaymentIntentが紐付かず、入金を追跡できない | 振込先表示前に `bank_transfer_previews` へPaymentIntent、顧客、金額、申込内容ハッシュ、連絡先を保存する。確認前入金もWebhookでプレビューへ記録し、申込者と管理者が追跡できるようにする |
| 2 | 入金後にカード等へ変更または振込先を取消すと、入金が顧客残高に残り二重支払い・返金対応になる | PaymentIntentの入金済額を再取得し、1円でも入金済みなら取消・支払方法変更を拒否する。管理画面へ要確認として表示する |
| 3 | 二重クリック、通信切断、再送により申込や決済が重複する | ブラウザが `client_submission_id` を発行し、D1で一意制約を設定する。銀行振込はプレビュー状態を条件付き更新して確定処理を占有し、PaymentIntentにも一意制約を設定する |
| 4 | 入金は確定したのに参加確定メールが失敗し、Webhookだけ処理済みになる | メール種別ごとの送信日時をD1に記録する。参加確定・不足入金メールが失敗した場合はWebhookを失敗扱いにして再送対象とし、安定した `message_id` で重複送信も抑制する |
| 5 | 過入金・未消込残高、確認前入金、処理途中の停滞を事務局が見落とす | `cash_balance.funds_available` を購読し、未消込金額と検知日時をD1へ保存する。管理画面に「銀行振込・要確認」を表示し、申込確定前入金・未消込・確定処理の停滞を一覧化する |

## 3. 申込フロー

### 3.1 共通

1. 申込者が本人情報、参加プラン、同伴者、懇親会、同意事項を入力する。
2. ブラウザとサーバーの両方で必須項目、料金、対象区分を検証する。
3. 確認画面で申込内容、割引、同伴者料金、支払予定額を表示する。
4. 申込者が「カード・スマホ決済等」または「銀行振込」を選択する。
5. 入金をWebhookで確認した時点で参加確定とする。画面遷移だけでは参加確定にしない。

### 3.2 カード・Apple Pay・Google Pay等

1. 申込確定時にD1へ申込を保存し、受付番号を発行する。
2. 外部決済画面を作成し、申込・支払レコードと結び付ける。
3. 申込受付メールを送信し、ブラウザを決済画面へ移動する。
4. 決済サービスのWebhookが金額、通貨、申込IDを照合する。
5. `paid` の場合だけD1を参加確定へ更新し、参加確定メールを送信する。
6. 領収書は決済サービスから入金確定後に送信する。通常、請求書PDFは自動発行しない。

### 3.3 銀行振込

1. 「振込先を確認する」で、顧客と銀行振込用PaymentIntentを作成する。
2. PaymentIntentを `bank_transfer_previews` へ保存してから、口座情報を画面に表示する。
3. この段階では受付番号を発行せず、申込確定メールも送らない。外部の正式な振込案内ページも開かせない。
4. 申込者が「この銀行振込で申込を確定する」を押す。
5. D1でプレビューを確定処理中へ更新し、申込・支払レコードを作成してPaymentIntentと紐付ける。
6. 受付番号、正式な振込案内リンク、未入金である旨をメールで送信する。
7. 不足入金時は支払予定額、入金済額、不足額、振込案内をメールで送る。参加は未確定のままとする。
8. 全額入金時に参加確定へ更新し、参加確定メールと領収書を送る。

表示される振込先は決済代行サービスが申込者ごとに生成・管理する仮想口座です。FANTASISTA会の通常の三菱UFJ銀行口座を画面へ直接掲載する設計ではありません。サンドボックスの「いろは銀行」等はテスト用表示であり、本番では決済代行サービスが発行した実在の振込先が表示されます。

## 4. メールのタイミング

| タイミング | 送信元 | 件名・目的 | 参加状態 |
|---|---|---|---|
| カード・スマホ決済等の決済前 | 送信なし | 決済照合用の仮データのみ保存し、申込完了とは扱わない | 未完了 |
| 銀行振込の申込確定直後 | FESTA事務局 | 受付番号、支払予定額、正式な振込案内、未入金 | 未確定 |
| 銀行振込の不足入金 | FESTA事務局 | 入金済額、不足額、追加振込案内 | 未確定 |
| 申込確定前に振込 | FESTA事務局 | 入金は確認済みだが申込確定が必要である旨 | 未確定・要対応 |
| カード・スマホ決済等の全額入金確認後 | FESTA事務局 | 申込完了・参加確定、受付番号、プラン、人数、チケット、当日案内 | 確定 |
| 全額入金確認後 | 決済代行サービス | 決済金額、領収書番号等 | 確定 |
| 未消込・過入金検知 | FESTA事務局内 | 金額、顧客ID、照合対象 | 管理者確認 |

申込受付メールが届かなくても、入金確認はWebhookとD1を正とします。参加確定メールの送信に失敗したWebhookは処理済みにせず再試行させます。事務局は管理画面のメール送信日時と要確認一覧を毎日確認します。

## 5. 主な状態

### 5.1 申込

- `pending`: 決済照合用の仮データ保存済み、オンライン申込は未完了
- `payment_pending`: 銀行振込待ちまたは非同期決済待ち
- `confirmed`: 全額入金済み
- `cancelled`: 取消
- `refunded`: 返金済み

### 5.2 銀行振込プレビュー

- `previewed`: 振込先表示済み、申込未確定
- `confirming`: 確定処理を占有中
- `application_created`: 申込作成済み、決済リンク処理中
- `linked`: 申込・PaymentIntent連携済み、入金待ち
- `funds_received_before_confirmation`: 申込確定前の一部入金
- `paid_before_confirmation`: 申込確定前の全額入金
- `unreconciled_funds_received`: 未消込残高あり
- `switched_to_online`: 入金前にカード等へ変更
- `cancelled`: 入金前に取消
- `paid`: 全額入金・申込連携済み

## 6. Webhook

本番とレビュー環境で、環境ごとに別の署名シークレットを使い、次を購読します。

- `checkout.session.completed`
- `checkout.session.async_payment_succeeded`
- `checkout.session.async_payment_failed`
- `checkout.session.expired`
- `payment_intent.succeeded`
- `payment_intent.partially_funded`
- `cash_balance.funds_available`

Webhookは署名、イベント重複、申込ID、金額、通貨を検証します。処理または必須メールが失敗した場合はイベントを `failed` とし、決済代行サービスからの再送で再処理します。

## 7. 管理画面と日次運用

担当者はCloudflare Accessで保護された `/festa60-admin/` を使用します。

毎日確認する項目:

1. 「銀行振込・要確認」が0件であること。
2. 不足入金と不足通知日時。
3. 未消込残高と検知日時。
4. 入金済み申込の参加確定メール送信日時。
5. 決済管理画面の失敗Webhookと待機中PaymentIntent。

確認前入金または未消込がある場合は、申込者へ連絡し、申込確定、追加振込、返金、手動消込のいずれかを判断します。D1だけを手作業で `paid` にせず、決済管理画面の実入金を必ず照合します。

入金がなく `previewed`、`cancelled`、`switched_to_online` のまま90日を超えたプレビューは、監査上必要な最小情報を確認したうえで削除対象とします。入金、申込、事故対応に関係する記録は会計・運営上の保存方針に従います。

## 8. 入金後の上位寄付プラン変更

入金後の申込者都合によるキャンセル、下位プランへの変更、寄付額の減額では返金しません。一方、通常参加からゴールドへ変更する場合など、上位の参加者向け寄付プランへの変更は受け付けます。

1. 申込者は受付番号と希望プランを事務局へ連絡する。
2. 担当者は元の申込、入金状況、現在プラン、割引区分、懇親会・同伴者情報を確認する。
3. 変更後プランの料金を、元の申込と同じ申込時期・卒部年度・懇親会条件で再計算する。
4. 変更後料金から既入金額を差し引いた額だけを追加請求する。金額が0円以下になる変更は受け付けない。
5. 追加決済は元の `application_id` と受付番号へ紐づく別の決済記録として保存する。元の決済記録を上書きしない。
6. 差額の全額入金後に `ticket_type`、チケット枚数、返礼内容を上位プランへ更新し、変更確認メールを送る。
7. 寄付を含むプランへ初めて変更する場合は、返礼発送先住所を確認する。
8. 当初分と差額分の領収書は決済単位で別々に発行する。管理画面では累計入金額と変更履歴を確認できるようにする。

当面は事務局受付による運用とし、申込者が公開画面から既存申込を直接変更できる機能は設けません。管理機能を実装する際は、Cloudflare Accessで保護された画面からのみ差額決済を作成し、監査ログへ変更前後のプラン、計算根拠、担当者、日時を記録します。

## 9. 本番反映条件

1. `20260808_harden_bank_transfer_flow.sql` をレビューD1へ適用する。
2. レビュー環境でカード成功、カード取消、銀行振込確認、銀行振込確定、不足入金、全額入金、二重送信、入金後変更拒否を確認する。
3. 管理画面でメール日時と銀行振込要確認一覧を確認する。
4. 本番Webhookに7イベントが登録され、失敗イベント通知を有効にする。
5. `CONTACT_EMAIL`、メール送信設定、署名シークレットが本番用であることを確認する。
6. レビュー結果について管理者の明示的な本番承認を得る。

この条件を満たすまでは、銀行振込を本番の公開支払方法として案内しません。

## 10. 参考仕様

- Stripeの銀行振込は、過不足金を顧客キャッシュバランスで管理する。
- `payment_intent.partially_funded` は不足入金後もPaymentIntentが `requires_action` のままであることを示す。
- `cash_balance.funds_available` は自動消込後に正の残高が残った場合の確認に使う。
- サンドボックスでは銀行振込案内メールの送信先に制約があるため、事務局メールの動作確認と決済サービス側のメール確認を分けて実施する。
